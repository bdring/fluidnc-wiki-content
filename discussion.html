Protocol Challenges

The Grbl protocol has some interesting characteristics that create challenges for FluidNC.  Grbl was designed with the assumption of an AVR microcontroller connected to a sender program over a serial line.  FluidNC has added new kinds of commands, plus a number of different connection options that sometimes clash with the original assumptions.

In the following discussion, “line” means a sequence of ASCII characters that is terminated with either CR, LF, or both.

Grbl

Grbl Flow Control

Most Grbl commands are line-oriented, in that nothing happens until a complete line (plus terminator) is received.  Since serial buffer space is limited, the sender must avoid sending data faster than Grbl can process it.  The flow control to prevent buffer overrun is done by acknowledging each line-oriented command with either an “ok” line or an “error: N” line. After receiving an acknowledgement, the sender can send the next line.  The sender is also permitted to count characters, sending extra lines into a serial buffer with an assumed max size, using the acknowledgments to keep track of how much space is left in the buffer.

Grbl Protocol Elements

The original Grbl protocol, as documented at <link>, has several kinds of “command” elements.

  1. GCode blocks:  GCode language statements are sent as lines.  They cause the machine to do things like move, turn on spindles and coolant, etc.  Most GCode blocks are asynchronous, in that Grbl receives the line, parses it, queues it for execution, then returns an “ok” response immediately, without waiting for the implied motion to finish.  A few GCode commands are synchronous, waiting untill motion is complete and the command has done its job before returning “ok”.  Synchronous GCodes include G4 (dwell) and spindle and coolant commands.  There is no inherent limit on how long this can take.
  2. Grbl configuration commands: Grbl is configurated via $<number> lines - $ followed by a number.  $<number> by itself results in a report of the associated value followed by an “ok” line, for example, if you send $10Grbl responds with
       $10=0
       ok
    You can set a value by sending a line $10=1, in which case Grbl responds with just “ok”.   The “set value” form only works in idle state - if you try to execute it when motion is in progress, it returns “error: 8”; otherwise it returns “ok” after the value has been set.  The “get value" form works in any state (except Critical Alarm).  It returns “ok” after returning the value, but it does not synchronize the planner buffer, i.e. it does not wait for in-progress motion to complete.
    There are a few other $ commands that also set or return information, like $#, $$, $G, typically behaving like $<number> with respect to when the “ok” is returned.
  3. Homing: $H lines and its axis variants $HX etc make the machine perform homing. It is synchronous, returning “ok” or “error:” only after the homing is complete.  This can potentially take a long time.
  4. Jog: $J=<stuff> makes the machine start moving.  It is asynchronous, returning “ok” or “error:” immediately, without waiting for the motion to complete.
  5. Realtime commands: Unlike the above commands which are all line-oriented, there are a few single-character commands that are processed immediately, without waiting for the reception of a complete line.  They can occur anywhere, even in the middle of a partial line.  They do things like reset (^X), feedhold (!), cycle start (~), request status report (?) and overrides for feed rate, spindle speed, and coolant (all non-ASCII characters with the high bit of the 8-bit byte set).  Realtime characters are not acknowledged via the “ok”/"error:" protocol and they do not count for buffer length character-counting.

Grbl Push Messages

In addition to the “ok” and “error: N” responses to line-oriented commands (which also serve as flow control), and the defined response data to $<num ber> commands that precede the “ok”, Grbl can issue some messages at times that do not correspond predictably to a previously-issued command.  Grbl calls these “push messages”.  The most important are Grbl: … (startup/reset), <…> (status report), ALARM: N  (alarm condition), and [MSG: …]  (feedback/extra information).  There are a few others like [GC:…] but they occur in response to specific commands before the “ok”, so they aren't really “push” (at any time), although they can be easily identified without needing the context of the command that triggered them.

<…> (status report) is sort of a special case in that it only occurs in response to the realtime character ? request, but since that character is not synchronized to line commands, it is hard to know exactly when the status report will come in, relative to other messages that are responses to line commands.

Grbl AVR Serial Line Characteristics

AVR Grbl has a single serial line with a buffer that is managed by an interrupt service routine (ISR).  The ISR code is part of the Grbl program, not an “under the hood” driver from a third-party library or framework.  The ISR code recognizes the special realtime characters directly, immediately setting corresponding flags that are later handled by the protocol engine code.  Non-realtime characters are buffered for later processing as GCode commands Grbl $ commands.  Realtime characters thus have a fast path that bypasses any form of queuing and does not have to go through any third-party system-level code.

Arduino Reset

Grbl originally ran on Arduino boards.  They typically had USB serial adapters that were wired so that the AVR processor would be reset if the USB cable was disconnected or if the host driver closed the connection.  One effect was that, when a sender opened the serial port driver, it would release the Grbl processor's reset line.  The processor would then start running Grbl and the sender could watch for the Grbl: startup message to know that it was talking to Grbl in a known initial state. Some senders depend on this behavior, assuming that a Grbl startup message will appear on the serial connection shortly after the USB port is connected.  If the sender does not see that startup message, it assumes that there is no Grbl controller on that port, and will not enable various UI controls.  This auto-reset-on-USB-connect behavior is a characteristic of the Arduino hardware that is not present on ESP32 modules; it cannot be controlled by firmware, so it is not possible for FluidNC to emulate it.

With some senders, it is possible to issue a CTRL-X reset, perhaps by clicking a reset or stop button.  When FluidNC (or Grbl) sees CTRL-X, it will stop what it is doing and issue a Grbl startup message, which will usually let the sender know that FluidNC (Grbl) is ready.

There are some AVR Grbl controllers that do not implement the auto-reset-on-serial-connect behavior, particularly ones that use a direct hardwired serial connection instead of emulating serial with a USB-serial chip.  For those controllers, the same sort of connection startup problem exists, so there is some incentive for sender developers to support non-auto-resetting Grbl controllers.

FluidNC

FluidNC Extra Commands

FluidNC adds a lot of additional commands to the standard Grbl set

  1. Named config commands: Lines like $Wifi/Mode or $Wifi/Mode=STA behave similarly to Grbl $<number> commands, reporting or setting configuration values and returning “ok” when done.  They differ from the corresponding Grbl commands primarily in the names (human-readable strings no number) and the values (again, strings not just numbers).
  2. Config tree commands: Lines that begin with $/ access elements in the configuration tree that is populated from the config.yaml file.  For example $/axes/x/steps_per_mm will respond with the current value of that tree item, while $/axes/x/steps_per_mm=200 will set a new value.  Unlike the non-/ config commands, tree value changes are not persistent; to make them persist you must edit the config file.  They behave the same with respect to the “ok” behavior.
  3. WebUI support commands: WebUI, which was originally developed by a third party, added some commands with names like [ESP800] to report information that WebUI needed.  There are also some corresponding “set” commands to change values.  FluidNC kept the “[ESPnnn]” names and also added aliases that conform to the $xxx naming convention, for example $Firmware/Info returns that same result as [ESP800].  Unlike the ordinary Grbl $ commands which return at most a single line of information, the WebUI commands can return a lot of information, potentially thousands of characters, as would be the case when listing access points, listing configuration items, or listing the file names on an SD card.  The original WebUI implementation of these commands would only work via HTTP GET, but FluidNC added the ability to use them from serial and other channels too.  In some cases the responses are encoded as plain text; in other cases the response is a JSON document.
  4. Filesystem commands: FluidNC supports managing files on the SD card and the local FLASH filesystem, with commands for displaying, deleting, uploading, etc from any channel including serial.  Some of the filesystem commands can generate long responses.
  5. Other information commands: FluidNC has commands for showing saved startup messages, lists of alarm codes and error codes, command names, and other helpful information.  The information precedes the “ok” response.
  6. Extended realtime characters: The recent work on serial-connected I/O extenders and pendants adds some additional realtime characters.  There aren't enough codes available in 8 bits for the events that we want to communicate, so we added the ability to send more realtime values encoded as UTF-8 sequences.

 

FluidNC Auto-reporting

FluidNC adds the ability to automatically issue status reports (<…>) and GCode mode reports ([GC:..]) when things change, avoiding the need for the sender to periodically poll by sending ? and $G .  That results in a more responsive user interface, since state changes can be noticed immediately instead of waiting until the next polling interval.  DROs can be updated faster since status reports are sent at a (configurable) rapid pace when the machine is moving.  Auto-reporting is enabled on a per-channel basis, so it only applies to senders that understand how to issue the $Report/Interval command that configures it.

FluidNC Channels

Unlike Grbl with its one serial line, FluidNC can be controlled from a variety of different communications channels, and more than one such channel can be active at once. The channels can be serial, disk, or network-based, and the network ones can be either one-shot request/response like HTTP or connection-oriented like TCP or websockets.  The variety and multiplicity of channels creates some interesting problems for Grbl protocol compatibility.

One problem is that the responses to commands coming in on a channel must go out on the same channel that issued the command.  But there are also some messages that need to go out on all channels, for example Alarm: reports. This is an important point that will crop up later…

Realtime commands also complicate the situation with multiple channels.  Most realtime commands do not result in any channel-specific output.  Instead they cause state changes that are presumably of interest to all senders. The glaring exception is the ‘?’ status request realtime command.  It asks for an immediate status report, which should go out on the channels that requested it.  Broadcasting a status report to all channels whenever any one of the issues a ‘?’ could cause a deluge of reports, especially when senders are configured to issue frequent requests (so as to notice state changes quickly and to update DROs rapidly).

 

FluidNC SD Card File Run Channel

FluidNC can run GCode files from an attached SD card, as opposed to Grbl which can only run GCode sent line-by-line over serial. When running an SD file, FluidNC must be careful about what it accepts from other channels.  It is appropriate to respond to realtime characters from serial, since they are used to pause and resume jobs and to overrides speeds. Line commands cannot be accepted from serial during as SD job run, because they could cause unpredictable operation as GCode commands from unrelated sources are interleaved.

Serial Channels

The FluidNC serial channels share a lot of similarities with the Grbl AVR serial connection, but there are also some subtle differences.  FluidNC runs on ESP32, using serial drivers from the Espressif ESP-IDF system code.  The interrupt service routine is in the ESP-IDF code and there is no easy way to get it to process Grbl realtime characters at the very low level where they are handled by the Grbl AVR serial ISR routine.  The ESP32 serial driver buffers all characters in the same way, so realtime characters must be picked-off at a later stage.  This causes problems when, for example, an SD card file run is in progress.  You need to process the buffered characters to find the realtime ones so they can, for example, pause the file run, but what do you do with any non-realtime characters that might have preceded them - since you cannot run line commands from serial during an SD file run?  (The current solution is to put them in a separate queue for processing later. You could discard them, but that might create problems with later characters that come in to form a now-garbled line.)

The possibility of multiple serial channels also creates problems.  Each serial channel needs its own queue because characters making up a line can come in at random times relative to the other channels.

The Arduino AVR “reset when USB serial is closed” behavior does not apply to ESP32 boards, so a sender cannot depend on FluidNC restarting every time that USB is opened.  That creates difficulties for senders, which must go to more effort to detect that FluidNC is present and determine its current state.  Overall, though, this is better than the “always reset” behavior, because it makes it possible to control FluidNC from the web, without unwanted resets from happening based on USB connections.

TCP Channels

FluidNC can use a TCP port as if it were a serial connection.  A sender that knows how to open a TCP connection can send commands and receive responses over the connection.  At the command/response level, the protocol is the same as for a serial connection.  There may be timing differences due to network latency and message packetization, but the data at the endpoint level is the same as serial.  As an example of possible timing differences, when you send a realtime character over a serial link, the timing is predictable, basically requiring one character time at the serial baudrate.  For a TCP connection, various elements in the network path might choose to buffer the character and forward it when some timer expires, or when something else happens. The particular set of Grbl realtime characters is not special to TCP networking, so there is little clue that they should be treated as urgent.

It can be tricky to determine exactly when a TCP connection is no longer active, and TCP connection closing can take a while to make sure both ends agree.

WebSocket Channels

WebSockets are like TCP connections that are dressed up in fancy clothes so that web servers and their associated software can use them. One advantage of websockets over a raw TCP connection is periodic pings, so it is easier to tell when the other end of a websocket is no longer alive.

WebUI uses a websocket for “push” communications like log messages and status reports whose timing cannot be directly correlated with a corresponding request.  Most of the messages that you see in the WebUI console come in via websocket.

When FluidNC restarts, perhaps from a crash or a user-initiated reset, the websocket connecting it to WebUI becomes stale.  Determining that this has happened in a timely fashion, so that WebUI can reconnect cleanly, is challenging.

HTTP Channel

FluidNC has a Web API that can be accessed by issuing HTTP GET requests to a “webserver” port.  WebUI uses it for a number of purposes, including

  • Initial access to the WebUI “index.html.gz” file via a GET request to the root route.  FluidNC “serves up” that file so the browser can run WebUI from the HTML and Javascript therein.
  • Getting information about FluidNC via the [ESP800] (aka $Firmware/Info) command.  WebUI won't start properly unless it gets a good response to that command.  The response must be contained in the “Response Data” of the HTTP request.  The URL is "http://<FLUIDNC_IP>/command?plain=[ESP800]&PAGEID=" (with the [ and ] characters URL-encoded per internet rules).
  • Reading various files like favicon.ico, macrocfg.json, and preferences.json.  The URL is, for example, http://<FLUIDNCIP>/macrocfg.json
  • Asking for a JSON-encoded list of files on the SD card, with a URL like http://FLUIDNCIP/upload?path=/ .  The “upload” route is used for a variety of SD file operations with different subcommands.  After one of those subcommands (or none), FluidNC returns the list of files in the response data.
  • Getting a list of FluidNC configuration items with the URL “http://FLUIDNCIP/command?plain=[ESP400]&PAGEID=”.  The list is JSON-encoded, returned in the HTTP GET response data.
  • Starting a websocket with the URL “ws://FLUIDNCIP:81/” .  Shortly after the websocket is created, there is an exchange of messages that include an “ACTIVE_ID:n” that establishes a “PAGEID” that is used later.
  • Issuing other commands with URLs like “http://FLUIDNCIP/command?commandText=$G&PAGEID=0” .  The number after PAGEID= is only present after a websocket has been set up.  It corresponds to the number from te ACTIVE_ID message mentioned above. If the PAGEID number is present, FluidNC can direct further push messages to that websocket.

A PAGEID number, identifying the websocket, is necessary because it is possible to run multiple instances of WebUI - on different machines or even on the same machine, thus you need some way to tell which one should get response data from, say a ? status report request. 

The need to send some data back in the HTTP response, while other data goes via websocket, creates a lot of confusing situations.  It is especially difficult in cases like $H homing, where the response is ostensibly synchronous (occurring before the “ok” ack that tells you that the command has been received successfully), but can take an arbitrarily long time to finish.  There is no systematic way to distinguish between commands with different response types, short of an exhaustive enumeration.

When the FluidNC webserver receives a command via HTTP, it needs to know the appropriate channel on which to return the response data - either in the HTTP response data or via the associated websocket - which might not have been created yet!  Realtime characters received via HTTP create yet another wrinkle, as they must be handled differently than line-oriented commands.

Some HTTP requests, notably [ESP800], are issued prior to the establishment of a websocket channel to the corresponding device.  The information from [ESP800] is needed in order to setup the websocket.
