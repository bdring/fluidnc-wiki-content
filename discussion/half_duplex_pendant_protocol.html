Goal

Use a half-duplex RS485 link as another way to hook up pendants.  Ordinary UART is fine for low-noise environments with short line lengths, but could have problems in high-EMI situations.  RS485, with its differential signaling, can have good noise rejection.  Typically it is half duplex so we would need some way to deal with that.  This outlines a possible way to send Grbl messages in a half-duplex fashion over RS485.

Basic Strategy

Encapsulate Grbl messages inside the half-duplex MODBUS protocol.  The “master” end - the “client” or master in MODBUS terminology - sends periodic requests, while the “slave”/“server” responds to those requests with data.  The master is the FluidNC end, while the pendant is the slave.  The master could be a FluidNC controller, or a smart I/O expander that connects directly to FluidNC via an ordinary UART and relays messages over RS485/MODBUS.

Instead of using the traditional MODBUS read/write registers model, we instead use a user-defined function code to wrap the GRBL line protocol in MODBUS frames.  We will use use function code 101 which is the last one in the user defined range, calling it GEP1 for Grbl Encapsulation Protocol version 1.  The function number 101 is ASCII ‘e’, which is not a standard GCode word, although it is used to mean “extruder” in 3D printing.  There are no other choices in the user-defined function space that do not collide with standard GCode words.  It would be possible to abuse a public function number like perhaps 64 ('@'), under the assumption that very few if any MODBUS devices in the field use that number, and it is highly unlikely that FluidNC would need to coexist with one.

It might be possible to use one multidrop RS485 bus for multiple devices, like a VFD and a pendant.  See the Coexistence section below.

Reasons for using MODBUS-RTU include

  • It is a well-understood half-duplex standard protocol that runs on RS485
  • The protocol overhead is not much
  • It has an address that can be used for multidrop communication
  • It has a CRC for message integrity
  • We already use it for VFDs, and there may be value in sharing one RS485 bus

Response Format

The data is anything that a sender could send to FluidNC over a UART channel.  If it includes realtime characters, they must be at the beginning.  If it includes line-oriented data, it must be complete lines.  More than one complete line can be included, subject to the overall length limitation.

Polling

The master must send requests periodically, even if it has no data to send (in which case the request data length will be 0). A request with no outgoing data (request data length = 0) is called a “nonce request”.  Periodic requests give the slave a chance to send data to the master.  The polling interval - the time between requests with no outgoing data - is configurable via an item in the channel section.

One approach might be to use periodic status reports as “polls”, but performance might be better if there are also nonce requests that are more frequent than status reports.

The slave must return a response packet for every valid request that it receives, even if it has no data to send.  The response must be received within (TBD) milliseconds after the request is received.  If the master does not receive a response, it can infer that the request was not received correctly or that the slave is not responding.  If the corresponding request contained data, the master may resend the same data once.

Interior Protocol

The messages that are sent inside the data fields are just like the normal Grbl protocol - GCode lines, $ commands, realtime characters, ok acks, error lines, [MSG lines, etc.  It is as if the MODBUS wrapping protocol is just a transparent container for ordinary Grbl communication.

Performance

Assume an RS485 baud rate of 115200, thus giving a byte rate of 10 bytes per millisecond.  A maximum-length message would thus take about 26 ms to send.  A request/response pair of maximum length would thus take 52 ms.  Maximum length messages in both directions would be quite rare though.  In nearly all cases, data is predominantly flowing in one direction at a time.

The protocol overhead for a request response pair is 5 bytes in each direction, occupying 1 ms of line time.

In the usual case for a jog pendant that is not a GCode sender, there would probably not be a data rate issue.  The majority of the traffic to the pendant would be status reports at, say 100 ms intervals.  The MODBUS encapsulation and the polling periodicity would barely affect that at all.  Furthermore, if FluidNC has data to send, it need not wait for a polling period if it has already received the response to the previous request.  The only “dead time” is just after a request has been sent, while waiting for the response or timeout.

A polling period (the time between nonce requests when nothing else needs to be sent) of 50 ms should be okay for interactivity when a pendant has commands like jogs.  When FluidNC has an ok ack to send back to the pendant, it could send it immediately since the line can be turned around right after the response packet that contained the command was done.  If the pendant had another command to send already queued up, it could send it as soon as it got the ack.  Thus, when there is rapid back and forth interaction, it would not be necessary to wait for a polling period.  The polling latency would only happen when back and forth message traffic subsides.

If the slave is sending rapid-fire GCode data, the master would primarily be sending 3-byte “ok\n” acks while the slave would be sending GCode.  Assuming an average GCode line length of 10 bytes, with 25 lines packed into a response message, the response message would take 26 ms while the request message would have 25 acks of 3 bytes for 75 bytes plus 5 overhead, so 8 ms.  Thus the pair would use 34 ms of line time.  

Improvements

It might be worthwhile to have a one-byte field in the request message with an “ok ack” count.  That would reduce the protocol overhead in the case where the slave is sending rapid-fire GCode.

Higher baud rates could also be used.

Coexistence with VFD Spindles

In principle, a pendant and a VFD could be on the same RS485 line.  They would have different addresses.  FluidNC would need a multiplexing routine to direct responses back to the code module that owns the addressed device.

Reliable Transport

It would be nice to have reliable transport of GCode.  Here are some ideas for that.

  • Reliability in the master-to-slave direction can be handled with timeouts and NAKs.  Since every outgoing request is supposed to elicit a response, the lack of a response is a clue that the request was not received or was garbled.  But it could also mean that the response was garbled, leading to replay errors.  That could be avoided with an incrementing sequence number, perhaps only one bit long.  If the slave receives a message with the same sequence number as the previous, it should be treated as a retry that resulted from a lost response.
  • Reliability in the slave-to-master direction could be handled in conjunction with “ok” optimization.  Suppose that the request message has two fields that report the number of ok's and the number of pending lines.  When the slave sends a batch of GCode lines to the master via a response, it counts the number of lines and also records the length of each line.  In the next request from the master, the numoks field tells the number of previously-sent lines have been okayed and the numpending field tells the number of received lines that have yet to be okayed.  The slave can use that to detect a lost response, because the GCode lines that were sent in that response will not be reflected in the counters.

This reliability mechanism could be applied to non-RS485 serial by omitting the address field and keeping the function code and CRC fields.
